# SA-6 security and observability checklist

Date: 2026-09-03 (Asia/Manila)
Scope: the Piso CAMP module — mobile app, API and admin web.

Every line below is either **asserted by a test that runs on every commit** or
**produced by a script anybody can re-run**. A checklist whose boxes are ticked
by hand records what somebody believed on the day they ticked it; this one
records what the code does today.

## 1. Mobile hardening

**Tokens and queues.** Session tokens, the guest pseudonym and the analytics and
survey queue keys live in `flutter_secure_storage` — Keychain on iOS,
EncryptedSharedPreferences on Android. The offline queues themselves are
**AES-GCM-256** encrypted (`EncryptedRecordQueue`), with the key held in secure
storage rather than in the file beside the data.

`security-controls.spec.ts` walks every Dart file in `apps/mobile/lib` and fails
if anything writes a token, secret, key or password through
`SharedPreferences.setString`: on a rooted device that store is readable by
anything.

**No hard-coded credentials.** `scripts/scan-hardcoded-credentials.mjs` looks
for the shapes a real leak takes — PEM private-key blocks, provider tokens with
known prefixes, connection strings carrying a password, secret-looking names
assigned long literals — across TypeScript, Dart, JSON, YAML, shell, Gradle and
plist files. It finds **0 blocking matches**; the 8 matches it does find are all
in files that declare themselves test-only or example, and each exclusion is
listed in the script with the reason it is safe.

The scan runs in the backend suite, so it fails a commit rather than a report
somebody reads later.

**Input validation and output encoding.** Every endpoint is contract-first: the
oRPC contract declares a Zod schema, and the schema is what the handler
receives. Responses are JSON produced by the serialiser, never string
concatenation. The one HTML-rendering surface in the stack is the OpenAPI
reference plugin, which was patched in this pass (`@orpc/openapi` stored-XSS
advisory).

## 3. Vulnerability scan

`pnpm audit` against the npm advisory database.

| | Before | After |
| --- | --- | --- |
| Critical | 6 | **0** |
| High | 100 | **0** |
| Moderate | 59 | 3 |
| Low | 17 | 1 |

Remediated by pinning patched versions through `pnpm.overrides` and by moving
three catalog pins forward:

- `next` 16.1.1 → **16.3.4** (13 advisories: middleware bypass, SSRF, DoS)
- `better-auth` 1.4.12 → **1.6.29** (9 advisories, one critical: OAuth
  refresh-token replay, account takeover via auto-linking)
- `@nestjs/common` / `@nestjs/core` → **^11.1.19**

Two changes needed judgement rather than a blanket bump, and both are recorded
in `pnpm-workspace.yaml` beside the rule:

- **`uuid`.** The generated rule matched `uuid@8` as well, and `>=11.1.1`
  resolves to 14.x, which is ESM-only. `exceljs` is CommonJS and requires
  `uuid@^8`, so the blanket rule broke AN-9's report export outright. Scoped to
  the 11 line; the advisory is a moderate buffer-bounds issue in v3/v5/v6
  generation with a caller-supplied buffer, which nothing here does.
- **`better-auth`.** Every advisory is patched by `>=1.6.22`, so the pin is
  1.6.29 rather than 1.7.x. 1.7 rescopes account identity by a new **required**
  `issuer` column, and running it against this schema failed every sign-up with
  a 500 — proved in the browser before rolling back. Taking a migration of the
  auth tables to fix advisories that 1.6 already fixes would have traded a known
  risk for an unknown one; the upgrade belongs in a ticket of its own.
- **`ajv`.** There is no patched release on the ajv 6 line, so `>=6.14.0`
  resolves to 8.x, and `@eslint/eslintrc` is written against the ajv 6 API —
  forcing it stops linting working at all. Left on 6.12.6: a moderate ReDoS in a
  dev-only linter dependency is not worth trading for a broken toolchain.

The remaining 3 moderate and 1 low advisories are all in development tooling
with no patched release available; none is Critical or High, which is what the
criterion asks for.

**Flutter.** `pubspec.lock` is inventoried above. Dart has no first-party audit
command; the packages are pinned and the inventory is what a scanner would be
pointed at.

## 4. Logging

Every request carries a correlation id: `genReqId` assigns one, and an inbound
`X-Request-Id` is **validated before it is trusted** — an id carrying a newline
is refused outright rather than trimmed, because a newline in a structured log
is a forged line.

Redaction is driven by one shared manifest (`@repo/observability`), applied in
two places because credentials travel in two: `PINO_REDACT_PATHS` for structured
fields, and `sanitizeLogUrl` for the query string, where Better Auth's
verification and reset links carry live single-use tokens.

Logged failure paths, each with the correlation id and no payload:

| Domain | Where |
| --- | --- |
| App / API | `pino-http` request logger, one line per request |
| Auth | Better Auth path, redacted headers and query |
| Sync | Analytics ingestion and bundle sync failures |
| Publication | Content workflow and bundle worker failures |
| Report | `AnalyticsController.runSafely` and the report export |
| Recognition, AR | **Not yet built** (AR-1…AR-3, DR-1…DR-4). The logging
  convention is the same one every other domain uses; there is no code to point
  at yet, and pretending otherwise would be the opposite of evidence. |

No log line carries a request body, an image, or a credential: bodies are not
logged at all, and the two redaction paths cover the fields and parameters that
could carry one.

## 5. What the upgrade broke, and how it was caught

The remediation is a dependency change, so it was verified the way a dependency
change has to be: by running everything.

- **`uuid` → 14.x broke the report export.** Four backend suites failed to load
  `exceljs`, which is CommonJS. Caught by the backend suite, fixed by scoping
  the override.
- **`better-auth` 1.7 broke every sign-up with a 500** — `The field "issuer"
  does not exist in the "accounts" Drizzle schema`. Caught in the browser, fixed
  by pinning the patched 1.6 line instead.
- **`ajv` → 8.x broke linting**, because `@eslint/eslintrc` is written against
  ajv 6. Caught by `pnpm lint`, fixed by leaving that one advisory accepted.
- **better-auth 1.6 typing.** `createAuth` was annotated
  `ReturnType<typeof betterAuth>`, which names the *default-options* instance;
  since 1.6 the instance is generic over the options it was given. The
  annotation is now inferred.

After the fixes: backend **111 suites / 988 passed**, Flutter **716 passed**,
web **492 passed**, contracts **377 passed**, auth **72 passed**, typecheck and
lint clean, and both applications build.

### Browser suite

Every Piso CAMP browser spec passes. A full `playwright test` run also surfaces
failures that predate this pass and are environmental rather than regressions:

- `submit-ticket`, `authenticated todos` and `cache-isolation` are template-era
  specs that sign **up** and expect a session. This deployment requires email
  verification before sign-in (a PRD decision), so a fresh sign-up correctly
  returns `token: null` and the browser is sent to `/login`.
- `cm2-assets`, `cm4-versions` and `cm5-preview` address seeded content by fixed
  id (for example `9c5b…0052`); those rows are not in this local database, so
  the pages redirect. `select count(*) from content_item where id = …` returns
  0.

A third class is cross-spec interference: several analytics specs share one
Playwright project and worker, and a spec whose last case signs in as a user
*without* the reporting permission leaves that session behind, so the next
spec's first page load records the 403s it expects to see none of. Every one of
those specs passes when run on its own, which is how each was validated when its
ticket was built.

None of the three classes is caused by the dependency work, and all are recorded
here rather than quietly filtered out of a report.

## 6. What this pass did not do

- **Penetration testing** is BSP-led and out of scope, as the ticket says.
- **Recognition and AR** log paths are listed above as not yet built.
- The scans here are static and advisory-database-driven. They are not a
  substitute for a DAST run against a deployed environment, which needs an
  environment this repository does not provision.
