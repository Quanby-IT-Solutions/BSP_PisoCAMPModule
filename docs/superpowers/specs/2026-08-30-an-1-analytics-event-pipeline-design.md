# AN-1 Analytics Event Pipeline Design

## Outcome

AN-1 establishes the single analytics path that every later Piso CAMP feature reuses. Mobile feature code emits only catalogued events. The SDK validates and durably encrypts each event before returning, retries batches whenever connectivity is available, and deletes only server-acknowledged events. The backend stores each client-generated `event_id` at most once and exposes a permission-gated count of today's `module_entry` events. The admin dashboard renders that count without requesting analytics data for unauthorized users.

The delivery guarantee is **at-least-once transport plus idempotent server insertion**, producing exactly one stored row per `event_id`. It does not claim distributed exactly-once execution.

## Scope and governing decisions

This design implements the AN-1 ticket, RF-2, and the Release 1 analytics walking skeleton. It activates the F1-reserved events `module_entry`, `account_prompt_shown`, and `account_prompt_guest`, and replaces CE-1's no-op `ContentViewAnalytics` bridge with `content_view` emission.

The following rulings are frozen for AN-1:

- The offline queue is a directory of independently encrypted event files, not a database and not one rewritable JSON document.
- Each event file is committed with a flushed temporary write followed by an atomic same-directory rename.
- Event plaintext is encrypted with AES-256-GCM using a random 96-bit nonce and a queue key stored only through `flutter_secure_storage`.
- The existing 22-character `device_pseudo_id` is the analytics subject for both guest and registered activity. `accountType` records the client state at occurrence time; it is descriptive data, never an authentication or authorization signal.
- The existing `piso_camp_device_account_link` remains the governed server-side path for future consent-scoped or registered-account reconciliation. AN-1 does not copy account IDs, names, or emails into analytics rows.
- Non-demographic pseudonymous usage analytics are operational analytics. The existing consent purposes continue to gate registration data, surveys, and demographic analytics; AN-1 does not add a new consent purpose.
- Reporting periods use `Asia/Manila`. The first tile counts events by `occurredAt`, so delayed offline uploads appear in the day on which the action occurred.
- The written spec and implementation are committed together only after AN-1 passes. This follows the user's one-PASS-ticket/one-local-commit rule; no design-only commit is created.

## Alternatives considered

### Selected: encrypted per-event files

One immutable encrypted file per queued event gives a small, auditable crash-consistency boundary. Ack deletion is naturally per event, a failed or interrupted write cannot corrupt unrelated events, and the implementation reuses the repository's existing `cryptography`, `path_provider`, and secure-storage dependencies. The storage implementation remains behind an interface so a later ticket can replace it without changing event producers.

### Rejected for AN-1: SQLCipher-backed SQLite

SQLCipher would provide indexed queries and efficient high-volume deletion, but AN-1 does not query the local queue. It adds native Android/iOS build, migration, and compatibility risk before volume justifies it. Server storage still uses PostgreSQL.

### Rejected: one encrypted JSON queue

A single encrypted document rewrites every event on append and acknowledgement. It creates an unnecessarily large corruption domain and cannot make concurrent append/delete operations safely atomic without rebuilding database semantics.

## Event catalog and common envelope

`docs/analytics-events.md` is the human-readable registry. Shared Zod contracts are the backend and web authority, while Dart mirrors the same closed catalog and exact-key rules. A feature must register a name and property schema before emitting it.

Every wire event contains exactly:

```json
{
	"schemaVersion": 1,
	"eventId": "UUIDv4",
	"eventName": "module_entry",
	"occurredAt": "UTC ISO-8601 timestamp",
	"subjectPseudoId": "22-character base64url device pseudonym",
	"sessionId": "UUIDv4",
	"accountType": "guest",
	"screen": "pisocamp_home",
	"feature": "module",
	"appVersion": "1.0.0+1",
	"osName": "android",
	"osVersion": "bounded platform version",
	"deviceCategory": "phone",
	"networkState": "online",
	"status": "completed",
	"properties": {}
}
```

The closed common values are:

- `schemaVersion`: literal `1`
- `eventId`: UUIDv4 generated once, before the local write
- `eventName`: a registered catalog name
- `occurredAt`: UTC, millisecond precision
- `subjectPseudoId`: `^[A-Za-z0-9_-]{22}$`
- `sessionId`: launch-scoped UUIDv4 generated by the SDK
- `accountType`: `guest | registered`
- `screen` and `feature`: catalog-controlled values, not arbitrary caller strings
- `appVersion`: bounded non-empty version/build string
- `osName`: `android | ios | other`
- `osVersion`: bounded non-empty normalized string
- `deviceCategory`: `phone | tablet | other`
- `networkState`: `online | offline | unknown`
- `status`: `completed | failed | cancelled`
- `properties`: the exact schema for the selected event; no unknown keys

`status` describes the feature action. It is distinct from the local transport state in DOMAIN-MODEL §4e: the existence of a committed queue file means `queued`, membership in the in-memory active batch means `uploading`, a returned ID means `acked`, and successful file removal means `deleted`.

AN-1 registers these event definitions:

| Event                  | Screen            | Feature              | Status      | Properties                | Emission point                                              |
| ---------------------- | ----------------- | -------------------- | ----------- | ------------------------- | ----------------------------------------------------------- | -------- | --------------------------- |
| `module_entry`         | `pisocamp_home`   | `module`             | `completed` | `{ entryPoint: navigation | deep_link                                                   | other }` | Once per module route entry |
| `account_prompt_shown` | `pisocamp_home`   | `account_prompt`     | `completed` | `{}`                      | Once when the optional-account prompt is actually displayed |
| `account_prompt_guest` | `pisocamp_home`   | `account_prompt`     | `completed` | `{}`                      | After guest continuation and pseudonym persistence succeed  |
| `content_view`         | `currency_detail` | `currency_education` | `completed` | `{ logicalId }`           | Once per opened CE-1 detail route                           |

`deep_link` is registered now so F5 can use the existing schema later; AN-1 emits `navigation` from the current route. A widget rebuild does not emit another logical view. A genuine later navigation creates a new event with a new ID.

The SDK accepts typed event intents rather than an unrestricted map. It still performs a recursive defense-in-depth scan before persistence. It rejects:

- keys equal to or containing normalized `email`, `name`, `image`, `photo`, `frame`, `token`, `cookie`, or `authorization`;
- byte arrays, files, URIs carrying data images, and base64-shaped image payloads;
- unknown keys, unsupported values, excessive nesting, oversized strings, and an event whose canonical JSON exceeds 8 KiB.

Rejection completes with a typed validation error and a debug-only, metadata-only developer log containing the event name and stable reason code. It never logs the rejected value. The backend repeats structural validation and size limits; client validation is not a trust boundary.

## Mobile components

The mobile subsystem has narrow interfaces:

1. **Event catalog/types** define the closed event intents and convert them to the common envelope.
2. **Analytics context provider** obtains the device pseudonym, launch session UUID, current account-type snapshot, connectivity snapshot, app version, OS version, and device category. The app version/build comes from platform package metadata, OS data comes from the Dart platform, and phone/tablet category comes from the root Flutter view's logical shortest side (`tablet` at 600 logical pixels or greater). All sources are injectable for deterministic tests.
3. **Analytics SDK** validates an event intent, constructs one immutable envelope, and awaits durable encrypted enqueue. UI integrations may intentionally detach the returned future through one guarded helper that reports only stable error codes.
4. **Encrypted event store** owns key creation, envelope encryption/decryption, atomic files, ordered batch reads, acknowledgement deletion, corruption isolation, and test-only inspection hooks.
5. **Analytics repository** sends validated batches through the existing Dio client and validates the exact acknowledgement response.
6. **Sync controller** serializes uploads, responds to startup/module-open/reconnect/manual triggers, and retries without mutating event identity.

The queue lives under the application-support directory:

```text
pisocamp/analytics/v1/
  queue/<eventId>.event
  quarantine/<eventId>.event
  tmp/<eventId>.<random>.part
```

The filename reveals only a random UUID. All event fields remain inside the ciphertext. The encrypted file is a strict binary envelope containing a format/version prefix, nonce, ciphertext, and authentication tag. AES-GCM additional authenticated data binds the format version and filename event ID, preventing a valid file from being renamed to another event ID. The key is a random 32-byte value stored under a versioned secure-storage key. A valid existing key is never silently replaced.

On initialization, orphaned temporary files older than 24 hours are removed because they were never committed; newer temporary files are ignored by readers and left for the process that created them. A file that fails envelope parsing, authentication, UTF-8/JSON decoding, filename/embedded-ID agreement, or current event validation moves atomically to quarantine and generates a count/reason diagnostic without event contents. Queue corruption never blocks later valid files.

If queue files exist but the secure key is missing or invalid, the store fails closed with `analytics_key_unavailable`; it does not generate a replacement key or delete unreadable events. This state is surfaced to observability and requires an explicit future recovery policy. Empty first-run storage generates and persists one key before accepting events.

## Mobile data flow and retry behavior

Emission follows this order:

1. Receive a typed event intent.
2. Capture common context and one UUIDv4 `eventId`.
3. Validate the complete event and the PII/image deny rules.
4. Canonically encode and encrypt with a fresh nonce.
5. Flush a temporary file and atomically rename it to `<eventId>.event`.
6. Return success to the caller; schedule sync if the connectivity snapshot is online.

The event is not considered emitted until step 5 succeeds.

Synchronization is single-flight across all triggers:

1. Enumerate committed filenames lexicographically, then read and decrypt at most 100 valid queued events while keeping the encoded request at or below 512 KiB. Ordering is deterministic but carries no reporting meaning; `occurredAt` remains the event-time authority.
2. POST the batch to `/api/v1/pisocamp/events` with the normal mobile API client. No per-batch idempotency key is required because each event owns its durable idempotency key.
3. Require a successful exact response containing distinct `ackedEventIds` drawn only from the submitted batch.
4. Delete only the files named in `ackedEventIds`; deletion is idempotent if a file is already absent.
5. Continue while a full batch was acknowledged and connectivity remains available.

There is no durable `uploading` rewrite. A batch is logically uploading only in memory, so process death or cancellation leaves the committed queue unchanged. A timeout, connection error, 5xx, malformed response, partial acknowledgement, or cancellation retains every unacknowledged file. While the process remains active, retry delay starts at 1 second, doubles to a 5-minute ceiling, and applies ±20% cryptographic jitter; a reconnect edge or later launch resets the delay and may retry immediately. Connectivity is a scheduling hint, not proof that HTTP is usable.

Permanent 4xx validation for a locally valid event is treated as a protocol defect: the batch remains queued, automatic tight-loop retries stop, and a stable diagnostic is logged. The SDK does not silently discard an event the server refused.

## Server contracts and persistence

The public ingestion contract is:

- `POST /api/v1/pisocamp/events`
- anonymous so guests can upload;
- strict throttle and existing correlation/error handling;
- JSON body `{ events: AnalyticsEvent[] }` with 1–100 events and a 512 KiB route/body limit;
- response `{ ackedEventIds: UUIDv4[] }` in request order.

The `analytics_event` table contains:

- `event_id` UUID primary key;
- the complete validated common fields using constrained text/enums and `timestamp with time zone`;
- `properties` JSONB limited by application validation;
- `received_at` server timestamp;
- indexes for `(event_name, occurred_at)`, `(subject_pseudo_id, occurred_at)`, and `(session_id, occurred_at)`.

It intentionally contains no account ID, email, name, IP address, user agent, raw image, authentication token, or unconstrained request metadata. Future tickets may resolve a pseudonym through the separately owned device-account link under their consent and reporting rules; they do not rewrite AN-1 event identity.

Ingestion validates the whole request before beginning a transaction. The transaction performs a multi-row `INSERT ... ON CONFLICT (event_id) DO NOTHING`. Every structurally valid requested ID is acknowledged whether inserted now or already present. An existing row is never updated by a retry, so a reused ID cannot mutate the original event. Database uniqueness is the concurrency authority.

This sequence covers the RF-2 failure branch: if PostgreSQL commits but the response is lost, the client resends the same immutable events, conflicts insert nothing, all IDs are acknowledged, and the client deletes them. Concurrent duplicate batches produce one row per ID.

## Dashboard query and permission boundary

The reporting contract exposes one read endpoint for the first tile. It calculates the current `Asia/Manila` calendar-day boundaries, converts those boundaries to instants, and counts `event_name = 'module_entry'` by `occurred_at` in the half-open interval `[start, nextStart)`.

The endpoint requires `reports.dashboards.view` through the existing F2 permission guard. A permitted registered user receives `{ date, timezone: 'Asia/Manila', moduleEntryCount }`. A user without the permission receives 403 and the existing guard writes `permission_denied`; an unauthenticated request receives 401 before permission resolution.

The existing dashboard overview adds one accessible stat tile. The analytics query is enabled only when `canAccess` confirms `reports.dashboards.view`, so unauthorized browsers do not issue a forbidden analytics request. The tile presents loading, zero, error, and success states without layout shift, exposes a meaningful label to assistive technology, and uses tabular digits. Other dashboard content remains unchanged.

## Failure handling and observability

All analytics diagnostics use stable operation/phase/outcome/reason fields and the existing error-reporting boundary. Permitted fields include batch count, acknowledged count, queue count, retry attempt, duration, HTTP status class, and stable reason code. Logs exclude event properties, pseudonyms, event/session IDs, local paths, response bodies, cookies, authorization data, and exception strings that may contain request data.

Expected behavior by failure class:

- **Validation or PII rejection:** no local file; debug-only developer diagnostic; typed error.
- **Encryption/key/write failure:** no committed event; temporary artifact cleaned when safe; error returned.
- **Single corrupt queue file:** quarantine that file; continue with other valid events.
- **Missing key with existing queue:** fail closed; retain ciphertext; stop upload.
- **Offline/timeout/5xx/cancellation:** retain unacknowledged files; retry later.
- **Partial valid acknowledgement:** delete only acknowledged IDs; retain the rest.
- **Malformed or foreign acknowledgement ID:** retain the batch and record a protocol error.
- **Duplicate server receipt:** insert zero duplicate rows and acknowledge the ID.
- **Dashboard query failure:** accessible tile error state; no sensitive server details reach the browser.

## Security and privacy properties

- AES-GCM provides confidentiality and authentication at rest; the OS keystore-backed secure-storage service protects the queue key.
- Every encryption uses a fresh cryptographically random nonce; tests prove nonce uniqueness for repeated plaintext.
- TLS remains the transport confidentiality boundary. The server accepts no client authorization claim from analytics metadata.
- Closed schemas and exact-key parsing prevent properties from becoming an accidental PII bucket.
- Both mobile and server enforce batch/event size limits before expensive processing.
- Anonymous ingestion is throttled. Event IDs and pseudonyms are high-entropy values; they are not reflected into logs.
- Database rows are immutable through the ingestion path. AN-1 exposes no raw-event listing endpoint.
- The dashboard returns an aggregate count only and remains behind the existing permission-and-audit spine.

## Testing and acceptance evidence

AN-1 completion requires fresh evidence at each layer.

### Contracts and catalog

- accept every registered event shape and all common enum values;
- reject unknown event names, unknown keys, invalid UUIDs/pseudonyms/timestamps, excessive sizes, and invalid event-specific properties;
- prove the Dart and TypeScript catalogs serialize compatible fixtures;
- verify `docs/analytics-events.md` matches the executable catalog.

### Mobile unit and filesystem tests

- prove a valid emission creates one non-plaintext authenticated file with the required metadata;
- prove email, name, raw bytes, image/data URI, unknown property, and oversize cases create no file and emit only safe diagnostics;
- prove atomic append under concurrent emissions, unique UUIDs/nonces, restart recovery, orphan-temp cleanup, corrupt-file quarantine, missing-key fail-closed behavior, and acknowledgement deletion;
- prove offline retention, reconnect batching, single-flight synchronization, partial acknowledgements, cancellation, timeout retention, and committed-timeout resend;
- prove `module_entry`, prompt, guest-choice, and CE-1 `content_view` emit exactly at logical interaction boundaries and not on widget rebuilds;
- run Flutter analyze, formatting check, focused tests, the full mobile suite, and an Android build.

### Database and backend tests

- verify the additive migration, constraints, indexes, primary-key uniqueness, and absence of PII columns;
- test valid batch insertion, exact acknowledgement order, duplicate resend, concurrent duplicates, no mutation on conflicting ID reuse, invalid/oversized batch rejection, and anonymous throttle behavior;
- use live PostgreSQL to prove a timeout after commit followed by resend leaves one row;
- test Manila day boundaries, zero count, delayed events, and neighboring UTC dates;
- verify permitted access succeeds, missing permission returns 403 plus `permission_denied` audit, and unauthenticated access returns 401 first;
- run focused tests, the full backend/contracts/database suites, lint, typecheck, and builds with clean server logs.

### Web and rendered validation

- test permission-gated query enablement and loading/zero/error/success tile states;
- exercise the dashboard in a real browser with permitted and denied users;
- confirm keyboard navigation, focus visibility, accessible name/value semantics, 320 px layout, 200% text, and no horizontal overflow;
- require a clean browser console, no unhandled rejection, and no unexpected or failed network request from the touched flow;
- run focused tests, the full web suite, lint, typecheck, and production build.

### Ticket evidence

`docs/pisocamp/an-1-acceptance-evidence.md` maps every Given/When/Then criterion and RF-2 step to commands, test names, database assertions, browser observations, server-log observations, and artifact hashes. AN-1 is not PASS until every row has direct evidence.

## Non-goals

AN-1 does not implement server-derived sessions, DAU/MAU, feature-usage KPIs, retention, demographic joins, raw-event browsing, report export, analytics opt-out/withdrawal, or a general-purpose arbitrary-property event bus. Those remain owned by AN-2 onward, AN-10, AN-9, and SA-7.

## Local delivery rule

After implementation, verification, acceptance evidence, and review all pass, the complete AN-1 change is staged and committed locally as:

```text
AN-1: add idempotent offline analytics pipeline
```

No branch, push, or pull request is created.
